Primary Token Types by Purpose
Access Tokens: The most common type of token, used to access protected resources on an API. They are generally short-lived (e.g., one hour) and must be included in the Authorization: Bearer HTTP header with every request.
Refresh Tokens: Long-lived tokens used to obtain new, valid access tokens after the current one expires, without requiring the user to log in again with their credentials. They are kept securely by the client and redeemed with the authorization server.
ID Tokens: Used in OpenID Connect (OIDC), these are JSON Web Tokens (JWTs) that contain information about the user's identity, such as their username and email. The application uses this information to personalize the user experience, but they should not be used to directly access APIs. 

Common Token Formats and Schemes
Bearer Tokens: This is a general class of token where access is granted to whoever possesses the token ("the bearer"). Access tokens and ID tokens are typically implemented as bearer tokens and require transmission over HTTPS for security.
JSON Web Tokens (JWTs): A specific, open-standard format for creating tokens that securely transmit information as a JSON object. They are digitally signed, making them self-contained and verifiable by the API without needing to constantly check a central database, which improves scalability for microservices. JWTs are often used as the format for both access and ID tokens.
API Keys: While often mentioned alongside tokens, an API key is a simple, unique string used primarily to identify the calling application and monitor usage, rather than an end-user's session. They are typically long-lived and offer less granular security compared to token-based systems like OAuth 2.0.
Authorization Codes: A short-lived, single-use token used as an intermediary during the initial login flow (e.g., in OAuth 2.0's Authorization Code flow). They are exchanged for actual access and refresh tokens at the backend, which prevents sensitive tokens from being exposed in a user's browser history or URL logs. 


OAuth2.0

Core Building Blocks of OAuth2.0
1. Roles (Actors)

Defined in the spec:

Resource Owner → the user who owns the data.
Client → the app requesting access on behalf of the user.
Resource Server → the API that holds the protected data.
Authorization Server → the system that authenticates users and issues tokens.
Can be separate (Google, Auth0) or self-hosted (IdentityServer, Duende).

2. Authorization Flows (Grants)

OAuth2 defines different flows for different scenarios:
Authorization Code Flow → standard for web apps (with PKCE for SPAs).
Client Credentials Flow → server-to-server (no user).
Implicit Flow → legacy, now discouraged.
Device Code Flow → login on TVs, IoT devices.
Password Grant → legacy, deprecated (was username/password exchange).

👉 Each flow defines how the client gets an Access Token.

3. Tokens

OAuth2 uses tokens for access and delegation:
Access Token → short-lived, sent in Authorization: Bearer <token> header.
Can be JWT or opaque.
Defines user identity + scopes.
Refresh Token → long-lived, used to get new Access Tokens.
Must be stored securely.
Can be revoked by server.
(Optional) ID Token → from OpenID Connect (OIDC), contains identity claims (profile, email, etc.).

4. Scopes & Claims

Scopes = what the client is allowed to do (e.g., read:books, write:books).
Claims = details inside the token about the user (e.g., sub, email, role).

5. Endpoints (Authorization Server)

A true OAuth2 Authorization Server must provide:
Authorization Endpoint → /authorize → where users log in & consent.
Token Endpoint → /token → issues access/refresh tokens.
Introspection Endpoint (optional) → validate opaque tokens.
Revocation Endpoint → revoke refresh tokens.
Discovery Endpoint (if OIDC) → /.well-known/openid-configuration (metadata for clients).

6. Consent & Delegation

Users can grant or deny specific scopes to a client.
Example: “This app wants to read your contacts.”

7. Security Best Practices

PKCE (Proof Key for Code Exchange) → required for public clients (SPAs, mobile apps).
HTTPS only → tokens must not travel over plain HTTP.
Token expiration → short-lived access tokens, long-lived refresh tokens.
Rotation → refresh tokens should rotate to prevent replay attacks.
Revocation → users/admins must be able to revoke tokens.

🔹 Putting It Together (Example with Google)

User tries to log in → redirected to Google /authorize.
User logs in & consents → Google redirects back with auth code.
Client exchanges code at /token → gets Access Token + Refresh Token (+ ID Token).
Client calls your API with Bearer <Access Token>.
Your API (Resource Server) validates token → grants access.
When token expires → client uses Refresh Token at /token again.

✅ So a “true OAuth2.0” system requires:

Authorization Server (with /authorize, /token, /revocation, etc.).
Resource Server (your API, validates tokens).
Clients (apps consuming APIs).
Tokens (Access + Refresh).
Scopes & Consent UI.

Flows depending on use case (Auth Code, Client Credentials, etc.).
